# Walkthrough: one earthquake, end to end

This follows a single earthquake from the ground to a Grafana panel. At each hop it names
the code, the Kubernetes object, and a command to watch that hop live on the k3s cluster.

Prerequisites: cluster running (`kubectl -n quake get pods` all `Running`), and for the
UI steps `scripts/ui.sh start`.

```
 seismometer ─► TexNet ─SeedLink─► ingest ─► Redis wf:0 / wf:1 ─► picker-0 / picker-1
                                                                        │ picks
                                                                        ▼
   Grafana ◄── Prometheus ◄── /metrics (every service)       Redis "picks" stream
                                                                        │
                                       Postgres ◄── associator ◄────────┘
                                       (events, picks)   └──► Redis "events" stream
```

| Kubernetes object | File | Runs |
|---|---|---|
| Namespace `quake` | `k8s/00-namespace.yaml` | boundary for everything below |
| ConfigMap `qd-config`, Secret `pg` | `k8s/10-config.yaml` | settings as env vars; DB credentials |
| Deployment + Service `redis` | `k8s/20-redis.yaml` | message bus |
| StatefulSet + Service `postgres` | `k8s/21-postgres.yaml` | storage, on a PersistentVolumeClaim |
| Deployment `ingest` | `k8s/30-ingest.yaml` | `services/ingest.py` |
| StatefulSet `picker` (2 pods) | `k8s/31-picker.yaml` | `services/picker.py` |
| Deployment `associator` | `k8s/32-associator.yaml` | `services/associator.py` |
| Deployment `prometheus` + RBAC | `k8s/40-prometheus.yaml` | metrics collection |
| Deployment `grafana` | `k8s/41-grafana.yaml` (generated by `k8s/src/make_grafana.py`) | dashboards |

## 0. The earthquake (t = 0)

A small event in the Delaware Basin, say M1.5 at 5 km depth. P waves travel ~5.5 km/s and
S waves ~3.1 km/s (the values in `qd-config` as `VP`, `VS`), so a station 10 km away sees
P about 2 s after origin and S about 3.5 s after.

## 1. Seismometer → TexNet

TexNet stations (network code `TX`) digitize ground velocity on three axes at 100 or
200 samples/s, pack it into miniSEED records of a few seconds each, and stream them to
TexNet's server at UT Austin. Nothing in this repo runs here.

## 2. TexNet → ingest (SeedLink)

**Code:** `services/ingest.py`, `services/common.py` (`get_stations`)
**Object:** Deployment `ingest`, 1 replica, `strategy: Recreate`

- At startup, `get_stations()` asks TexNet's FDSN station service for TX stations inside the
  box, and its SeedLink server which ones it streams. The list goes into Redis under the key
  `stations`, so the associator uses the same list.
- `Feed.on_data()` is called once per arriving miniSEED record. It looks up the station's
  shard with `shard_of()` (a CRC32 checksum of the station code modulo `SHARDS`; Python's
  `hash()` changes per process, a checksum does not) and appends the record to Redis stream
  `wf:<shard>`.
- Every 5 s at most it touches `/tmp/heartbeat`. The liveness probe restarts the pod if
  that file is more than 120 s old, i.e. if no data has arrived for 2 minutes.

**Why `Recreate`:** a rolling update starts the new pod before stopping the old one. Two
ingest pods would publish every record twice.

**Watch it:**
```bash
kubectl -n quake logs deploy/ingest | head -1          # station list and shard assignment
kubectl -n quake port-forward deploy/ingest 9100:9100 &
curl -s localhost:9100/metrics | grep qd_ingest_last_sample | head -5
kill %1
```

**Time budget:** a record leaves the station when it fills, so data reaches ingest about
1–3 s after the ground moved (the "data lag" panel).

## 3. Redis waveform streams

**Code:** `Bus.publish_trace()` / `Bus.to_trace()` in `services/common.py`
**Object:** Deployment `redis`

Each entry holds the trace id (`TX.PB28.00.HHZ`), start time, sampling rate, and samples
as float32 bytes. Streams are capped with `MAXLEN` so memory stays bounded.

**Watch it:**
```bash
kubectl -n quake exec deploy/redis -- redis-cli XLEN wf:0
kubectl -n quake exec deploy/redis -- redis-cli XLEN wf:1
```
Run them twice a few seconds apart: the counts grow until they hit the cap.

## 4. Pickers: PhaseNet

**Code:** `services/picker.py`
**Object:** StatefulSet `picker`, 2 replicas → pods `picker-0`, `picker-1`

- Each pod finds its shard from the number at the end of its own hostname (`my_shard()`).
  This is why it is a StatefulSet: pod names are stable and ordered, so `picker-1` always
  owns `wf:1`, even after it is deleted and recreated.
- It reads its stream continuously into a per-station buffer of the last 90 s (`KEEP_S`).
- Every 10 s (`STEP_S`) it runs PhaseNet on the whole buffer (`model.classify`). This is
  the only neural network in the system.
- A pick is kept only if it is more than 5 s (`EDGE_S`) from either end of the buffer
  (the model has not seen the full waveform there yet) and is not within 0.5 s of a pick
  already sent (the buffer overlaps itself cycle to cycle, so the same arrival is found
  repeatedly).
- New picks go to Redis stream `picks`.

**Watch it:**
```bash
kubectl -n quake logs -f picker-0                       # "shard 0: N sta, infer X s, +k picks"
kubectl -n quake exec deploy/redis -- redis-cli XREVRANGE picks + - COUNT 3
```

**Time budget:** a pick is accepted on the first cycle where at least 5 s of data follow
it, so 5–15 s after the arrival reaches ingest.

## 5. Associator: picks → earthquake

**Code:** `services/associator.py`
**Object:** Deployment `associator`, 1 replica, `Recreate` (it must see every pick)

- Reads every pick, writes it to Postgres table `picks`.
- When new picks have arrived (or an event is waiting to settle), runs PyOcto on the last
  300 s of picks (`ASSOC_S`). PyOcto searches the box in space and time for a source whose
  predicted P and S times match picks at several stations. An event needs at least 6 picks
  (`N_PICKS`) and 3 stations with both P and S (`N_PS`).
- An event is reported only once its origin is 30 s old (`SETTLE_S`), so distant stations'
  S waves have arrived and been picked. Then it is written to Postgres table `events`,
  published to Redis stream `events`, and counted in the latency histogram.
- An event within 3 s and 15 km of one already reported is not reported again.

**Watch it:**
```bash
kubectl -n quake logs -f deploy/associator              # EVENT lines
kubectl -n quake exec -it postgres-0 -- psql -U quake -c \
  "select origin_utc, lat, lon, n_sta, latency_s from events order by origin_utc desc limit 5"
```

**Time budget:** reported 30–40 s after origin (settle time plus up to one 10 s cycle).
This wait dominates detection latency; everything upstream finishes well inside it.

## 6. Postgres: the record

**Object:** StatefulSet `postgres` with a `volumeClaimTemplate`

The data directory sits on a PersistentVolumeClaim; k3s backs it with a directory on the
node's disk. Deleting the pod does not delete the data.

**Watch it:**
```bash
kubectl -n quake get pvc
kubectl -n quake exec -it postgres-0 -- psql -U quake -c "select phase, count(*) from picks group by phase"
```

## 7. Prometheus and Grafana: seeing it

**Objects:** Deployment `prometheus` + ServiceAccount/Role/RoleBinding; Deployment `grafana`

- Each service serves metrics on port 9100 (`prometheus_client`).
- The pod templates carry annotations `prometheus.io/scrape: "true"` and
  `prometheus.io/port: "9100"`.
- Prometheus, using its ServiceAccount (allowed only to read pods in `quake`), lists pods
  from the Kubernetes API, keeps the annotated ones, and scrapes them every 15 s. A new pod,
  such as a third picker, is found automatically.
- Grafana's data source and dashboard come from ConfigMaps, so the dashboard is code.

**Watch it:**
- http://localhost:9090/targets: 4 targets, all UP
- http://localhost:9090/graph: try `time() - qd_ingest_last_sample_unixtime`
- http://localhost:3000: the "Quake detector" dashboard

| Panel | Query (simplified) | What it shows |
|---|---|---|
| Data lag per station | `time() - qd_ingest_last_sample_unixtime` | hop 2 delay; a rising line = stalled station |
| PhaseNet inference | `rate(..._sum) / rate(..._count)` | hop 4 compute per cycle |
| Association time | same pattern, `qd_assoc_seconds` | hop 5 compute per run |
| Detection latency | `histogram_quantile(0.5 / 0.9, ...)` | origin to report |

## 8. The latency budget, assembled

| Hop | Typical time after origin |
|---|---|
| P wave reaches near stations | 1–3 s |
| Record reaches ingest | +1–3 s |
| Pick accepted | +5–15 s |
| Event settles and is reported | 30–40 s total |

## Drills: break it on purpose

| Drill | Command | What to watch |
|---|---|---|
| Lose a picker | `kubectl -n quake delete pod picker-1` | New `picker-1`, same shard; its log stream ends with `stopped cleanly` (SIGTERM handling) |
| Lose the database pod | `kubectl -n quake delete pod postgres-0` | Comes back; `select count(*) from events` unchanged (PVC) |
| Change a setting | edit `THRESH` in `k8s/10-config.yaml`, `kubectl apply -f k8s/`, `kubectl -n quake rollout restart statefulset/picker` | Picks per minute changes in Grafana. Pods read env vars only at start, hence the restart. |
| Starve the feed | turn the VPN on *without* the MSS clamp | Data lag climbs, ingest restarts after 120 s with no data; turn it off and it recovers |
| Scale pickers to 3 | set `replicas: 3` in `31-picker.yaml` and `SHARDS: "3"` in the ConfigMap, apply, restart ingest | `picker-2` appears; ingest log shows a 3-way shard map; Prometheus finds the new pod by itself |

## Incidents found while building it

| Problem | Symptom | Root cause | Fix |
|---|---|---|---|
| ObsPy 1.5 SeedLink client | crash on connect | connect compares elapsed time to a `None` timeout; the same attribute also caps stream duration | set the timeout only around `connect()` |
| VPN MTU, Docker | station list times out; small requests fine | tunnel MTU 1414 < Docker bridge 1500; "too big" signals lost | `--network host`, or compose network MTU 1400 |
| VPN MTU, k3s | ingest restart loop (23 restarts) | same, one layer deeper: pod MTU 1450 > tunnel 1414; VPN auto-reconnects on wake | MSS clamping on the host (`mss-clamp.service`) |
| redis-py 8 default | associator crash: "Timeout reading from socket" | new 5 s default socket timeout < 10 s blocking read | explicit 30 s socket timeout, reads capped at 5 s |
| Liveness vs startup | pods killed while still starting | fixed `initialDelaySeconds` shorter than a slow start | startup probes (10 min allowance), then liveness |
| Association cost | cycle time grew 10 → 14 s with >100 picks held | PyOcto re-ran on all picks every cycle | separate service; runs only on new picks or a pending event |
